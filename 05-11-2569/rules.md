# กฎการทำงานและเงื่อนไขสำคัญของระบบ

เอกสารนี้เป็นข้อกำหนดที่ต้องตรวจสอบทุกครั้งก่อนพัฒนา แก้ไข หรือทบทวนระบบ NKW Student Care เพื่อป้องกันระบบเสียหาย ข้อมูลคลาดเคลื่อน และพฤติกรรมที่ไม่ตรงกับงานของโรงเรียน หากข้อกำหนดใดขัดกับพฤติกรรมปัจจุบันของระบบ ให้ตรวจสอบผลกระทบและยืนยันแนวทางก่อนเปลี่ยนแปลง

## 1. Backend และฐานข้อมูล (Google Sheets และ Apps Script)

- **เขตเวลา:** ห้ามใช้ `new Date().toISOString()` เพื่อสร้างวันที่หรือเวลาสำหรับข้อมูลของระบบ เพราะได้เวลา UTC ซึ่งอาจทำให้วันคลาดเคลื่อนจากเวลาไทย 7 ชั่วโมง ให้ใช้ `getLocalDateStr()` หรือ `Utilities.formatDate` โดยกำหนดเขตเวลา `Asia/Bangkok` เสมอ โดยเฉพาะข้อมูลช่วงหลังเที่ยงคืนถึงเช้ามืด
- **รหัสที่มีเลขศูนย์นำหน้า:** Google Sheets อาจแปลงรหัส เช่น `01383` เป็น `1383` ให้ใช้ `getDisplayValues()` เมื่อจำเป็นต้องรักษาค่าตามที่แสดงในชีต และ normalize รหัสอย่างสม่ำเสมอขณะเปรียบเทียบ เช่น ตัดเลขศูนย์นำหน้าด้วย `.replace(/^0+/, '')` โดยต้องไม่ทำให้รหัสคนละคนถูกมองว่าเป็นคนเดียวกัน
- **ค่าคาบเรียนใน Timetable:** Sheets อาจตีความค่าอย่าง `1-2` เป็นวันที่ ให้ดึงค่าจาก Display Values หรือ normalize ค่า Date กลับเป็นข้อความคาบเรียนก่อนนำไปใช้
- **การเขียนข้อมูลพร้อมกัน:** ครอบการบันทึกที่อาจชนกันด้วย `LockService.getScriptLock()` และปล่อย lock อย่างถูกต้อง เพื่อป้องกันครูหลายคนบันทึกทับกัน
- **เวลาประมวลผลและแคช:** คำนึงถึงข้อจำกัดเวลาทำงานของ Apps Script (โดยทั่วไปไม่เกิน 6 นาที) และ timeout ของหน้าเว็บ/การเรียกใช้ฝั่ง client (ประมาณ 15–30 วินาทีตามบริบท) งานที่อ่านข้อมูลจำนวนมาก เช่น Sync วินัยหรือดึง Timetable ควรใช้ `CacheService` เมื่อเหมาะสม พร้อมกำหนดวิธีหมดอายุและทำให้แคชเป็นปัจจุบันหลังมีการเปลี่ยนแปลงข้อมูล
- **การบันทึกซ้ำ:** การบันทึกที่เป็นการแก้ไขข้อมูลเดิมต้องค้นหาแถวเดิมและอัปเดต หรือลบข้อมูลเดิมตามกติกาที่กำหนดก่อนเขียน ห้ามใช้ `appendRow` อย่างเดียวจนเกิดแถวซ้ำ

## 2. Frontend และการแสดงผล (HTML, JavaScript และ UI/UX)

- **มือถือและ Safe Area:** ออกแบบ mobile-first รองรับหน้าจอมือถือจริง ใช้ `env(safe-area-inset-bottom)` เมื่อเหมาะสมกับอุปกรณ์ที่มี safe area และทำให้ Bottom Navigation แบบ sticky/fixed ไม่หลุดหรือบังเนื้อหาระหว่างเลื่อน
- **ปุ่มสถานะสม่ำเสมอ:** ปุ่มสถานะ มา/ขาด/สาย/ลา/ป่วย ในระบบเช็คแถว เขตพื้นที่ และเรียน ต้องใช้ขนาด สี และแอนิเมชันที่สม่ำเสมอ โดยสีหลักคือ เขียว/แดง/เหลือง/ฟ้า/ม่วง ตามลำดับสถานะที่กำหนดในระบบ
- **ป้องกันการกดซ้ำและจัดการข้อผิดพลาด:** เมื่อเริ่มบันทึก ให้แสดง Loading Overlay และป้องกันการส่งซ้ำ จัดการ timeout และข้อผิดพลาดจากการเรียก Apps Script ด้วย failure handler ที่เหมาะสม และมี Retry เฉพาะเมื่อปลอดภัยต่อการบันทึกซ้ำ ห้ามปล่อยให้หน้าเว็บค้างหรือแจ้งผลสำเร็จทั้งที่บันทึกไม่สำเร็จ
- **Iframe cache busting:** URL ของ iframe สำหรับหน้าเช็คเขตพื้นที่/เช็คเรียนต้องมี query parameter เช่น `?v=Date.now()` เพื่อให้โหลดโค้ดล่าสุด โดยต้องรักษา query parameter เดิมที่จำเป็นไว้ด้วย
- **วันที่ที่ผู้ใช้เห็น:** วันที่ใน UI ต้องแสดงเป็นภาษาไทย เช่น `1 พ.ย. 2569` หรือ `1 พฤศจิกายน พ.ศ. 2569` ห้ามแสดงรูปแบบดิบ `YYYY-MM-DD` ให้ครูเห็น

## 3. ความปลอดภัยและสิทธิ์ (Security และ RBAC)

- **ตรวจสอบสิทธิ์สองชั้น:** การซ่อนปุ่มหรือจำกัดหน้าใน Frontend ไม่เพียงพอ ทุกการดำเนินการสำคัญต้องตรวจสิทธิ์ซ้ำใน Backend ก่อนอ่านหรือเขียนข้อมูล เช่น `saveAttendance` ต้องตรวจว่าครูที่ส่งมามี `classroom_ids` ตรงกับ `room_id` ที่ร้องขอจริง ห้ามเชื่อ role หรือข้อมูลผู้ใช้จาก client โดยไม่ตรวจสอบ
- **ขอบเขตของแต่ละ Role:**
  - `director`: ดูข้อมูลได้ทุกอย่าง และเป็นผู้อนุมัติเอกสาร
  - `discipline`: ทำงานกิจการ/วินัยได้ ยกเว้นอนุมัติเอกสาร
  - `teacher`: ดูสถิติได้ทุกห้อง แต่เช็คชื่อได้เฉพาะห้องที่รับผิดชอบ
  - `council`: ช่วยเช็คแถวและเขตพื้นที่ได้ แต่ห้ามเช็คเรียนหรือจัดการวินัย
  - `student`: เข้าถึงได้เฉพาะข้อมูลของตนเอง
- **Logout และ Session:** เมื่อ Logout ต้องล้าง `localStorage` ที่เกี่ยวข้อง เช่น `teacher`, `student`, `selected-date` และคืน UI ไปหน้า Login ทันที ห้ามค้างหรือเปิดเผยข้อมูลจากหน้าหลักเดิม

## 4. กติกาธุรกิจและ Workflow

- **การคำนวณความเสี่ยง:** คะแนนความเสี่ยงคำนวณจากแถว 40%, เขตพื้นที่ 30%, เรียน 30% และต้องใช้ Dynamic Weights: หากช่วงนั้นไม่มีข้อมูลกิจกรรมใดเลย ให้เฉลี่ยน้ำหนักของกิจกรรมที่มีข้อมูลจริงใหม่ ไม่ถือกิจกรรมที่ไม่มีข้อมูลเป็น 0% เช่น หากไม่มีข้อมูลเขตพื้นที่ ให้นำ 70% ที่เหลือไปเฉลี่ยระหว่างแถวและเรียน เพื่อไม่ให้ผู้เรียนเสียคะแนนโดยไม่มีข้อมูลรองรับ
- **ลำดับขั้นวินัยและระยะเวลา:**
  - Stage 1 → 2: ต้องผ่านอย่างน้อย 7 วันหลังสร้างเคส และนักเรียนยังอยู่ในสถานะเหลือง/แดง
  - Stage 2 → 3: ต้องผ่านอย่างน้อย 14 วัน และนักเรียนยังอยู่ในสถานะแดง
  - Stage 3 → ปิดเคส: ต้องให้ครูกด “ผ่านกิจกรรม” ก่อนเท่านั้น ห้ามข้ามขั้น
- **การอนุมัติเอกสาร:** เอกสาร “ทัณฑ์บน” และ “แจ้งผู้ปกครอง” ที่ครูจัดทำต้องอยู่ในสถานะรออนุมัติ และถือว่าสมบูรณ์เมื่อ ผอ. อนุมัติในระบบแล้วเท่านั้น

## 5. การสร้างและพิมพ์เอกสาร

- **รูปแบบ A4:** เอกสารราชการใช้กระดาษ A4 ฟอนต์ `TH Sarabun PSK` ขนาด 16pt ระยะบรรทัด 1.5 และขอบกระดาษตามแบบที่กำหนด โดยเว้นซ้าย 2cm และระยะย่อหน้า 2.5cm ตรวจสอบการพิมพ์จริงก่อนเปลี่ยน CSS ที่เกี่ยวข้อง
- **ขาวดำ:** เอกสารราชการต้องพิมพ์ขาวดำ ไม่มีตัวอักษรหรือป้ายสี เช่น คำว่า “ใกล้ชิด” ให้ใช้ตัวหนาสีดำ ไม่ใช้สีแดง
- **ตราครุฑ:** อ่านรูปจาก Config (B14) หรือ Base64 ให้แสดงในขนาดที่เหมาะกับหน้ากระดาษ หากรูปใช้ไม่ได้ต้องแสดง fallback เป็น 🦁 แทนพื้นที่ว่าง
- **ช่องลงนามและวันที่:** ต้องมีช่องลงนามนักเรียน ผู้ปกครอง ผอ. และพยานครูที่ปรึกษา/งานกิจการฯ วันที่ในเอกสารต้องมาจาก Timestamp จริงของระบบและแสดงตามรูปแบบวันที่ไทย เช่น `5 / 11 / 2569` ห้ามปล่อยเป็นจุดไข่ปลา `.....`

## 6. กฎการทำงานและการดูแลประวัติ

- ก่อนแก้ไขทุกครั้ง ให้พิจารณาผลกระทบระยะยาว ความเสี่ยงที่ระบบหรือข้อมูลจะเสียหาย และผลกระทบต่อหน้าจอหรือ workflow อื่นที่เกี่ยวข้อง
- ทำความเข้าใจพฤติกรรมเดิมและตรวจสอบพื้นผิวที่เกี่ยวข้องก่อนแก้ไข รักษาความสอดคล้องระหว่าง Backend, Frontend, สิทธิ์, ข้อมูล และเอกสาร
- เมื่อทำงานเสร็จ ให้บันทึกใน `todo.md` ว่าทำอะไร เสร็จแล้วได้อะไร และควรทำอะไรต่อ พร้อมบันทึกตามลำดับเพื่อให้ติดตามและย้อนรอยการทำงานได้
- อัปเดต `todo.md` ทุกครั้งที่งานเสร็จ ห้ามเขียนทับประวัติเก่าโดยไม่จำเป็น
- ใช้ Git history/commit เมื่อมีการใช้งาน Git เพื่อย้อนคืนการเปลี่ยนแปลงจริง; `todo.md` เป็นบันทึกการทำงาน ไม่ใช่สิ่งทดแทนระบบควบคุมเวอร์ชัน
